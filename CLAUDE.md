# growth-skills — project memory

A Claude marketplace and plugin, `growth-skills`: screen teardowns for growth work on mobile subscription apps, for product designers. Author: Ivan Polushin (theoutlines). Public repo, MIT.

## Product split (agreed 2026-10-30)
- `subscription-skills` (theoutlines/subscription-skills) = the paywall and its numbers: benchmark reports (RevenueCat, Adapty, FunnelFox), Pricing Index, benchmark router, store compliance, Adapty's paywall-teardown and A/B test assistant. Self-contained product.
- `growth-skills` (this repo) = the journey around the paywall: web funnel, onboarding, the onboarding↔paywall seam, upsells, retention to first renewal, cancel flow, plus `growth-router`, `growth-map` (what the app doesn't do at all) and `funnel-check` (own numbers vs benchmarks) and `test-readout` (read a finished A/B test: trust checks, range, where the difference came from) and `variant-check` (paywall or onboarding A vs B before launch: mechanics, can the test see it as built, what winning versions had, clarity pretest). It keeps growing (non-subscription directions later: currency, one-time purchases, etc.).
- One plugin, one install: `growth-skills` includes copies of the 8 Subscription Skills skills. The Claude app doesn't auto-install plugin dependencies (tested 2026-10-30: only growth-skills was added), so dependency + git-subdir was dropped in v1.1.0.
- Source of truth for those 8 skills stays in theoutlines/subscription-skills. Never edit them here: run `scripts/sync-subscription.sh` before each release (it also copies the CC BY 4.0 licence into `LICENSES/`).
- Claude app rules learned: a git source `url` must be a full `https://` URL (shorthand is skipped); plugin description ≤500 characters; SKILL.md description ≤1024; the app strips `supportUrl`, `privacyPolicyUrl` and `icon` with a warning (keep them, the directory reads them). Adding a marketplace in the app doesn't add its plugins: the user still adds the plugin from Discover.
- Standalone skill repos are retired. Skills are edited only here, in `plugins/growth-skills/skills/`.

## Layout
- `.claude-plugin/marketplace.json` at the root (one entry); plugin at `plugins/growth-skills/` with its own `plugin.json`.
- Skills (19): our `growth-router`, `growth-map`, `funnel-check`, `test-readout`, `variant-check`, `web2app-teardown`, `onboarding-teardown`, `flow-teardown`, `upsell-teardown`, `retention-teardown`, `cancel-flow-teardown`, plus the 8 synced from subscription-skills. Each teardown has `SKILL.md`, `references/` (incl. `ranges.md`), `scripts/` (`render_report.py`, `test_duration.py`, `example.json`), `assets/fonts` (Inter, OFL). `growth-map/references/levers.md` maps 42 levers to teardown patterns; `funnel-check/scripts/test_duration.py` is a copy.
- `evidence/tests.csv` is the single source of truth for test rows (290 records incl. outcome win/loss/null/mixed/none, bundled, mechanics, checked). Edit the base first, then `python3 scripts/evidence.py build` (writes the rows into each `evidence.md`) and `check` (0 problems before a push; CI runs it). `evidence/planner-ideas.csv` maps every planner idea to its records; the check compares it with the planner's `data.js` when cloned next to this repo.
- `ranges.md` per teardown: min–max of measured lifts per pattern and metric, built only from that skill's `evidence.md`; vendor bands, self-selected comparisons and rows whose source doesn't match are left out (listed in each file's Checks). Rebuild a skill's ranges when its evidence changes.
- Evidence IDs per skill: onboarding #1–#77 and E1–E8 (shared with flow-teardown), upsell #U, cancel #C, web2app #W, retention #R (regulator rows in retention platform-rules use D). Rows copied between libraries keep their original number in a "Same as" note; never renumber.
- Raw research lives outside the repo: `/home/claude/onboarding-teardown-research/`, `/home/claude/upsell-research/`, `/home/claude/cancel-flow-research/`, `/home/claude/web2app-research/`, `/home/claude/retention-research/`.

## Rules
- Purpose: tools for product designers in the AI era. Only what a designer changes on a screen is scored, recommended or mentioned. No PM, engineering, push/CRM programme, payment-setup or legal-ops content.
- Never invent a number. Every figure links to its source with a tier: strong, directional, anecdotal, observed. On-target evidence beats strong evidence; bundled tests cap a row at Medium; never merge two tests into one number.
- Never reward pressure or friction. Flags are design rules with a source name, not legal advice.
- Rubric rules shared by all teardowns: full / half (round down) / zero; unseen → half held back; one issue, one deduction; blockers cap the total at 49; held back ≥10 shown; up to 8 rows, never pad.
- Buckets = RevenueCat SOSA categories; "AI app" is a tag. Keep metric definitions apart (per install / trial start / paywall view / session / subscription).
- Mobbin content is described in our own words, never copied; example teardowns don't name the app. Public sources only; no employer data. Walkthroughs never enter a name, phone, password or payment data and never skip a gate by URL.
- Test changes with independent subagent runs on the same briefs (scores must reproduce within a few points). Run `claude plugin validate .` before every push. Bump `version` in plugin.json and the marketplace entry on every release, and add `.github/release-notes/vX.Y.Z.md`. Pushing the version change to main runs `.github/workflows/release.yml`, which zips each skill and publishes the release (tag pushes and the releases API are blocked from this session, so the workflow does it).

## Decisions (2026-10-30, owner review)
- **Show a "range seen" next to each test idea**, like Adapty's expected-impact ranges, because it gives a feel for the size of the win. Build it only from measured results in `evidence.md`: the lowest and highest lift seen in published tests of the same kind of change, on the same metric, with the number of tests ("+8% to +36%, 3 tests"). One test → its own number. No test → "no published range". Label it "seen in published tests, not a forecast for your app". It's a range of results, never a merged average.
- **Nudge toward real data.** Every teardown ends with one line saying the ranking and durations get sharper on the user's own funnel numbers, and, when an analytics connector (Amplitude, Mixpanel, RevenueCat, Adapty) is available, offers to pull them. A reminder, not a gate.
- Owner's goals for the whole toolset: help him (a growth design lead building a Growth team) collect hypotheses, analyse current data against benchmarks, design variants, check them before hand-off, and learn the full growth toolkit, including where the team does nothing yet.
